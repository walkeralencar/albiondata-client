# 0.1.56 Analysis: Non-GUI Adoption

## Executive decision

Do not merge or cherry-pick `master` wholesale. The current branch (`fyne`, `23903dd`) and local `master` (`1e8abb5`, tag `0.1.56`) diverge from tag `0.1.55` (`519ecb5`). All application changes on `master` arrived through the Wails dashboard series, while the current branch retains the pre-Wails client and adds repository documentation and the agent squad.

Adopt selected backend fixes as new, narrowly scoped changes. The strongest candidates are:

1. make a failed interface capture non-fatal;
2. correct Windows physical-address length handling;
3. rescan network interfaces and safely retire vanished interfaces;
4. fix NSIS release version detection;
5. improve CI test coverage and remove duplicated build definitions, using a CLI-compatible workflow;
6. fix formatting scripts so vendor exclusion is effective;
7. document Windows capture, build, and updater constraints after reconciling them with the current architecture.

The Wails dashboard, Svelte frontend, dashboard status/counters, console and window-state packages, dock integration, and GUI-specific build dependencies are intentionally excluded and are not recommended.

## Recommended changes

### P0: isolate capture failures per interface

**Master source:** `f65087b`, primarily `client/listener.go`.

Master replaces `log.Panic` when `pcap.OpenLive` or `SetBPFFilter` fails with an error log and return. This is a high-value reliability fix: listeners are started in separate goroutines, and an unrecovered panic terminates the whole process, including capture on otherwise usable interfaces. A virtual adapter that cannot be opened should not disable every physical adapter.

Adopt the behavior, but harden lifecycle ownership while doing so:

- return a result or completion signal to the watcher so failed listeners are not retained as if active;
- make `stop` idempotent and safe before handle initialization;
- avoid unsynchronized reads and writes of `listener.handle` between startup, rescan, shutdown, and the run loop;
- define exactly one owner responsible for closing the pcap handle;
- test open failure and BPF failure through an injectable opener/filter boundary rather than requiring live capture.

**Compatibility:** No payload, topic, privacy, or protocol change. Startup becomes more tolerant. Logging changes are user-visible but compatible.

### P0: respect `PhysicalAddressLength` on Windows

**Master source:** `f65087b`, `client/net_interface_filter_win.go` and its tests.

The current helper formats all eight bytes of Windows' fixed physical-address array. Master passes `PhysicalAddressLength` and formats only the valid prefix. This prevents a zero-length address from becoming an artificial all-zero MAC that can collide with pseudo-interface filters.

This fix is small, separable, and backed by focused tests on master. Port the helper and table-driven tests. Confirm the expected treatment of invalid lengths greater than the fixed array: returning an empty address is conservative, but the caller's filter semantics should be asserted explicitly.

**Compatibility:** Windows-only capture candidate selection changes. Some adapters previously filtered out can become candidates, which makes the per-interface failure isolation above a prerequisite.

### P1: dynamically reconcile capture interfaces

**Master source:** `ec1989a` and `3ca2474`, primarily `client/albion_watcher.go`, `client/listener.go`, and `client/albion_watcher_test.go`.

Master re-enumerates interfaces every ten seconds, creates listeners for new devices, and stops listeners for vanished devices. This addresses VPN adapters appearing or disappearing after client startup and is valuable independently of any GUI.

Adopt the capability after the P0 lifecycle work, but redesign rather than copy literally. The master implementation has risks that deserve resolution:

- a listener that fails during asynchronous startup remains in watcher bookkeeping;
- `listener.device` and `listener.handle` participate in asynchronous lifecycle operations without an explicit synchronization contract;
- `stop` sends on a channel and also closes a handle while the run loop may close it again;
- periodic polling is embedded in a `default` branch with `time.Sleep`, which makes shutdown and deterministic testing less direct than a ticker-based loop;
- device identity is a string and duplicates are not normalized before the set diff;
- no test exercises races, shutdown during startup, repeated stop, or a failed listener followed by a rescan.

Use a ticker, explicit listener states, idempotent cancellation, and completion cleanup. Keep `diffDevices` or an equivalent pure set-diff helper and retain its table-driven tests. Run the race detector where libpcap dependencies permit.

**Compatibility:** Capture availability improves, especially with VPNs. No ingest contract changes. Additional interface enumeration and log messages occur every reconciliation interval.

### P1: fix Windows installer version derivation

**Master source:** `f65087b`, `pkg/nsis/Makefile`.

Master replaces the obsolete `CIRCLE_TAG` input with validated `GITHUB_REF_NAME`, strips an optional `v`, and falls back to `0.0.1` for non-tag refs. The current release process uses GitHub Actions, so this fixes misleading Windows file metadata.

Adopt with tests or scripted checks for `0.1.56`, `v0.1.56`, a pull-request ref, an empty ref, and the repository's historical four-component tags such as `0.1.46.1`. Master's three-component regular expression rejects those historical versions. Decide whether future releases require strict SemVer or whether NSIS metadata should map a fourth component deliberately.

**Compatibility:** Installer metadata only; release asset names should remain unchanged.

### P1: stop bundling legacy WinPcap, with a non-GUI warning path

**Master source:** `f65087b`, `pkg/nsis/albiondata-client.nsi`, `internal/pcapdriver/`, and `docs/windows-capture-pcap.md`.

Moving users from the bundled legacy WinPcap installer to Npcap is directionally sound for modern Windows and VPN compatibility. The installer-side detection and official download link are reusable without the dashboard. The runtime `internal/pcapdriver` decision logic is also cleanly separated and tested, but master surfaces its result through GUI status.

Before adoption:

- verify current Npcap redistribution and installation guidance from authoritative sources;
- decide how the existing non-GUI client surfaces a persistent actionable warning (log plus native notification or systray action);
- preserve passive capture and explain the security tradeoff between all-users and administrator-only driver access;
- verify registry views and access behavior on supported Windows targets;
- confirm the installer does not imply that installation succeeded when capture remains unavailable;
- retain the old installer file removal as a separate, auditable repository change.

Do not port dashboard status fields or Wails browser links.

**Compatibility:** Material Windows installation change. Existing installations may retain WinPcap; the updater only replaces the executable, so runtime guidance is important. Harbor should lead, with Gauge and Scribe review.

### P1: improve CI without importing frontend requirements

**Master source:** `f65087b`, `.github/workflows/build.yml`, `release.yml`, and `test-build.yml`.

The reusable build workflow reduces drift between pull-request and release builds, and master adds `go vet ./...` and `go test ./...`. Adopt the architecture, not the files verbatim. Master's workflow configures Node and relies on GUI-aware build scripts, so it is not suitable for the current branch as written.

A CLI-compatible workflow should:

- use `go-version-file: go.mod` consistently;
- build Linux, Windows, and macOS through the repository scripts;
- run vet and tests after installing libpcap development headers;
- preserve the exact existing release asset names consumed by the updater;
- avoid Node, GTK 4, WebKitGTK, Wails, and frontend cache configuration;
- validate the Windows installer version and updater archive names;
- keep release upload permissions explicit and minimal;
- confirm whether `actions/checkout@v6`, `setup-go@v6`, and artifact actions are supported by the repository's GitHub environment before changing versions.

The macOS script cleanup in master contains useful native-amd64 build knowledge, but its frontend build and broader GUI assumptions must be removed. Treat macOS changes as a separate Harbor-reviewed item.

### P2: repair formatting script scope

**Master source:** `f65087b`, `scripts/fmt.sh` and `scripts/validate-fmt.sh`.

Master correctly identifies that passing package directories to `goimports` can recurse into `vendor/` despite filtering the directory list. Selecting Go files explicitly avoids that behavior. Port the concept, but use null-delimited file handling (`find ... -print0` with `xargs -0`) or another space-safe approach; master's command substitution breaks on paths containing whitespace and can exceed command-line length limits.

Also remove the stale `echo $CIRCLE_TAG` from validation. Verify both scripts with and without a vendor directory.

**Compatibility:** Developer tooling only.

### P2: reconcile vendor policy

**Master source:** `f65087b`, removal of `vendor/`, `.gitignore`, and module metadata changes.

Master removes the vendor tree. The current project guide already notes that the checked-in vendor tree can be incomplete and recommends `GOFLAGS=-mod=mod`. A single dependency policy would reduce confusion, but vendor removal should not be copied as part of the GUI squash.

Choose and document one policy in a dedicated change:

- remove vendor contents, ignore `vendor/`, build from verified module downloads, and ensure CI runs `go mod verify`; or
- regenerate a complete vendor tree intentionally and make CI use it.

Do not adopt master's `go.mod` wholesale: it adds Wails, raises the Go version, removes the current systray dependencies, and updates transitive modules for GUI needs. Dependency security and Go-version updates require a separate review.

### P2: adopt selected repository hygiene

**Master source:** `f65087b` and `9009a59`, `.gitignore`.

Potentially useful patterns are `/.albiondata-client*` for updater backup files, `*.syso` for generated Windows resources, and `*.tmp`. Reconcile them with the current `.gitignore` and preserve the current devcontainer decision. Ignore entries for specific external tools should be added only if those tools are actually used by this repository.

### P2: incorporate technical documentation selectively

**Master source:** `9e35e56`, especially `docs/windows-capture-pcap.md`, `docs/build-and-release.md`, and `docs/self-update.md`.

These documents contain useful operational reasoning, but they describe the Wails-era build and runtime. Merge verified facts into the existing `PROJECT_GUIDE.md` or add focused documents after each corresponding backend change lands. Avoid copying `CLAUDE.md`; the repository already has `AGENTS.md`, `.agents/`, and a documentation index.

## Overlap with the current branch

The current branch's five unique commits add devcontainer handling, `AGENTS.md`, detailed project/release documentation, and the `.agents` squad. Master does not contain those files and a wholesale merge would delete or conflict with much of this work in the resulting tree comparison.

Relevant overlaps are:

- `docs/PROJECT_GUIDE.md` already documents capture, updater, build, vendor, privacy, and lifecycle constraints; master documentation should supplement it, not replace it.
- `docs/CHANGELOG.md` and `docs/RELEASE_HISTORY.md` stop at `0.1.55`; if selected `0.1.56` behavior is ported, document the new branch's actual release rather than claiming the GUI release was adopted.
- `.gitignore` has current-branch devcontainer changes; reconcile individual patterns rather than replace the file.
- `AGENTS.md` assigns platform/capture work to Harbor, tests to Gauge, and documentation/release review to Scribe. These adoption tasks should follow that routing.
- Application code on the current branch is effectively the `0.1.55` baseline, so backend diffs can be extracted against the known merge base without first untangling other application changes.

1. **Capture failure isolation** — Harbor lead; Gauge review. Establish idempotent listener lifecycle first.
2. **Windows MAC-length fix** — Harbor lead; Gauge review. Land with Windows-specific unit tests after step 1.
3. **Dynamic interface reconciliation** — Harbor lead; Atlas and Gauge review. Include race and shutdown tests.
4. **Formatting script fix** — Gauge lead; Atlas review. Low-risk tooling improvement that simplifies later validation.
5. **NSIS versioning fix** — Harbor lead; Gauge and Scribe review. Decide four-component-version handling explicitly.
6. **Npcap migration and warnings** — Harbor lead; Gauge and Scribe review, Atlas integration. Verify current licensing guidance before implementation.
7. **CLI-compatible reusable CI** — Harbor lead; Gauge and Scribe review. Preserve updater/release asset contracts.
8. **Vendor-policy decision** — Atlas lead; Gauge review. Keep separate from dependency upgrades.
9. **Documentation reconciliation and release notes** — Scribe lead; affected technical owners review.
10. **Optional encryption correlation redesign** — Atlas lead; Cipher/Relay as needed and Gauge review. Proceed only after shared-state synchronization is explicit.

Each step should be a separate, reviewable change. No step requires adopting GUI code.

## Verification plan for implementation

Documentation analysis alone does not prove the master fixes on supported systems. During adoption, require:

- focused unit tests for address formatting, device diffs, lifecycle idempotence, and failure paths;
- `go test ./...` with libpcap development headers installed;
- `go test -race ./client/...` where CGO/libpcap support permits;
- Windows compilation and Windows-specific tests for interface filtering, registry decision logic, and installer generation;
- a controlled Windows smoke test with a physical adapter and a VPN adapter appearing and disappearing;
- Linux and macOS builds through the same scripts used by CI;
- inspection of release archives and exact updater asset names;
- `make validate-fmt` and `git diff --check`;
- no calls to real ingest services in automated tests.

## Remaining risks

- The master commit messages report real Windows/VPN observations, but this review did not have the original capture logs or a Windows host to reproduce them.
- Interface lifecycle code interacts with blocking libpcap handles and goroutines; copying master's code without an ownership redesign can replace a crash with leaks, races, or shutdown hangs.
- Npcap licensing, installer options, registry layout, and download guidance are external facts and must be reverified at implementation time.
- Release workflows are an updater contract. A workflow cleanup that changes file names or architectures can strand installed clients.
- The current shared `albionState` is already accessed concurrently. Additional correlation state should not land until its synchronization model is defined.

## Final recommendation

Treat `master` as a source of evidence and patches, not as an integration target. Extract the two small P0 capture fixes first, then implement interface reconciliation on a safer lifecycle foundation. Follow with installer and CI improvements adapted to the existing non-GUI client. Preserve the current documentation and squad structure, and keep every Wails/dashboard/frontend concern out of the adoption series.
